================================================

You can leave the SGE_SESSION_FILE as-is: 
     SGE_SESSION_FILE: ./sge/sge_contact.txt 

Then make a 'sge' folder in your resources folder. There is no need to create 
the file. 

To use sge for all GenePattern jobs you can set the executor in the 
default.properties section. 

default.properties: 
     executor: SGE 

The other options (setting it in user.properties, group.properties, or 
module.properties) are only needed if you want to customize your server to use 
different queuing systems based on the user or the module. 

To help with debugging, make some edits to the 
./Tomcat/webapps/gp/WEB-INF/classes/log4j.properties file. 
# debugging SGE integration 
log4j.logger.org.broadinstitute.zamboni=DEBUG, stdout 
log4j.logger.org.genepattern.server.executor.sge=DEBUG, stdout 

You need to restart your server for this to take effect. 

Regards, 
Peter

Yes, that is helpful. You need to add the appropriate SGE library to your LD_LIBRARY_PATH before starting the server.
For our installation, I run this line before starting the server.
    export LD_LIBRARY_PATH=${LD_LIBRARY_PATH}:/broad/gridengine/lib/lx24-amd64

FYI, we include a version the required DRMAA java library in the GenePattern install.
    ./Tomcat/webapps/gp/WEB-INF/lib/sge-drmaa.jar
It can't hurt to replace this with the drmaa.jar that is part of your SGE system.

Regards,

How can I set multiple queues where GP can submit jobs? Should this be done while creating different SGE executors or just adding another queue name to queue name paramter?

The default 'sge.queueName' can be set as a global property; It can be customized on a per-user, per-group, or per-module basis in the config_yaml file. There is a deterministic order of precedence, but to make your life easy I recommend organizing by module name. That seems to work best for our team.

For example,
    SGE:


        classname: org.genepattern.server.executor.sge.SgeCommandExecutor
        configuration.properties:
            # SGE config variables, see the SGE doc for more explanation
            SGE_ROOT: /var/lib/gridengine


            # ...
        default.properties:
             sge.queueName: main.q

module.properties:
    # custom sge queue by module name
    ConvertLineEndings:
        sge.queueName: cle.q
    # custom sge queue by module lsid
    " urn:lsid:broad.mit.edu:cancer.software.genepattern.module.analysis:00002:1":
        sge.queueName: cle.q

group.properties:
    test_group:
        sge.queueName: group.q

user.properties:
    test_user:
        sge.queueName: user.q

Btw, we are working on improvements which make it possible for you to prompt for a queue name from the user interface. 

Regards,
Peter

Remind me what version of GP you have running. Newer versions allow you to 
include custom job queue parameters on the job input form. 
For example, to enable this for all users, add this line to the 
'default.properties' section of your config_yaml file: 

     job.inputParams: "sgeInputParams.yaml" 

Save the attached sgeInputParams.yaml file into your resources folder. Make

For the memory flag we set a range of values in the 'job.memory' menu, something 
like, 
     job.memory 
     choices: [ "2 Gb", "8 Gb", "32 Gb", "128 Gb", "512 Gb=max available (512 Gb)" ] 
We don't have support for a concept of job.memory=MAX 

We don't support custom complex variables from the job input form. Let me know 
your specific requirements, and we can take it under consideration as a new 
feature request. 

The newer Grid Engine code (which we use for in-house Univa Grid Engine 
integration) uses more general param names such as 'job.memory' and 'job.queue' 
for customization. 
     https://github.com/genepattern/gp-jobrunner-drmaa_v1 
It is ready for beta use with other DRMAA v1 capable Grid Engine systems but we 
have not tested it. 

We recommend using these param names to pick up a couple of extra features of 
our system. 
* built-in parser to resolve human readable memory flags (e.g. 'job.memory=4 Gb' 
is properly understood at runtime) 
* initialization of optional default 'job.memory' flag from the module manifest. 
This makes it unnecessary to manually edit the config file for large memory jobs. 
* common flags are portable to other integrations (e.g. SLURM, PBS/Torque, and LSF)
