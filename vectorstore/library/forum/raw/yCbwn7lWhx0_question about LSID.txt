Hi Stephane,


For your module, '57' is the lsid identifier. When you create a new module in the GUI, the server uses the next available integer as the unique identifier. So, in a way, yes, the number is related to the number of modules created on your server. A numerical value is not strictly necessary. If you want to use a different identifier, I suggest using a non-integer value to avoid a conflict. However, it is a bit tricky to make changes of this kind and still use the GUI, aka module integrator, for making edits.


Here is the template for an LSID:
  urn:lsid:{authority}:{namespace}:{identifier}[:{version}]

For your module,
  authority=8100.admin.MAF-SRV-04.maf-srv-04.med.ad10.intern.kuleuven.ac.be
  namespace=genepatternmodules
  identifier=57
  version=0.4.2



By comparison, here's the LSID for the ConvertLineEndings module:
  LSID=urn:lsid:broad.mit.edu:cancer.software.genepattern.module.analysis:00002:2
  authority=broad.mit.edu
  namespace=cancer.software.genepattern.module.analysis
  identifier=00002
  version=2


Regards,
Peter

Update: Don't change the lsid.identifier to a different integer value. It will conflict with modules created in the GUI.


More specifically, the lsid identifier assigned by the GUI does not account for identifiers from modules which are installed from a zip file. I did not test with modules installed from a repository such as GParc or Broad repos. I suspect it will be a problem there as well.


In case you are interested ... I tested this by creating a new module in the GUI. Lsid identifier was automatically created as '12'. Next I created a different module by hand with lsid identifier set to '13', then uploaded from zip. Next I created a new module in the GUI. It was given the same identifier '13'. To clean up, I deleted the conflicting module from the Manage Modules page.

Update: Don't recycle existing module lsids. This creates more problems.

For best results ...
* do not use the same base LSID for two different modules
* do not use the same name for two different modules

As you discovered, module versions are grouped by base lsid and not by name.

I create the initial version in the GUI. The server will generate a valid lsid with a unique (to the server) lsid identifier. I recommend the following recipe.

Step 1: Create initial version in the GUI.
   -- assign it a unique name
   -- start with a minor or patch level version to indicate pre-release status, e.g.
        Version Increment: 'New patch version (v0.0.1)'

Step 2: Export as zip. Save the manifest file into your project working directory. I usually rename it to track the version number, e.g.
  mv MyModule.zip MyModule_v0.0.1.zip

When updating the module, before installing from zip, edit the manifest file.
* Increment lsid version, e.g. LSID=....:0.0.2
* add a version comment, e.g. comment=Added new feature

Regards,
Peter
