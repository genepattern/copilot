Hi Bam,

 

I'm pretty sure the issue here is the great deal of NaN values in the dataset. From the dataset it appears the input you're using is log transformed RSEM counts, is it possible that when this conversion was done a pseudocount of 1 was not added to the data resulting in all of the 0 values becoming NaN? If so, I might suggest reconverting the data but instead using log(RSEM+1). However, we don't really recommend using counts data for ssGSEA, something more appropriate might be TPM (or log(TPM+1), as this would prevent the length of the gene from influencing it's contribution to the enrichment score.

 

Let me know if you have additional questions here,

 

-Anthony

As stated earlier, often there is a stray value that is not quite formatted right. Like a weird scientific notation. Inspect all the values or move them to another place like excel and use the sort function which should bring problem values to the top or bottom. If you are positive there is no stray characters, try to copy and paste data to a new file and make sure you format as numbers. If all else fails try the clean function in excel to remove unwanted characters. Of course, this assumes your input files have the correct input formatting

Hello,


The actual issue here appears to be something related to the container exiting. This can occur when the job attempts to exceed the server limits defined at runtime.

In the "Job Options" section, you can see that these jobs were run with the default parameter of 2GB of memory, and a two hour maximum runtime. I would suspect that this was an issue with the memory requirement in particular. Try increasing this to 16GB and rerunning. If it still doesn't work we can try digging into the server logs to get more information as to why this is happening.
